# Feature: Knit web interface (`knit ui`)

Objective: a local web app that joins Claude and Cursor into one workflow (plan with Claude → orchestrate with Knit → implement with Cursor), saves tokens, and is the single place to review everything. Design: [docs/web-interface.md](../../docs/web-interface.md).
Branches: one per slice, stacked (see D12) · Phases: A (live view + run control) → B (Claude workspace and plan handoff) → C (Cursor follow-ups) → D (agent configuration) → E (file explorer, later) · Delivery: ask-on-risk, chain strategy `stacked-to-main` (chosen L15) · Tests: vitest (`pnpm test`), plus typecheck.

## Specs

User's words are quoted verbatim (Spanish, as written). Everything else is marked as a derived constraint or an assumption.

- **S1** Scope: "Hagamos este ODD detallado sobre la interfaz web".
- **S2** Look and feel: "una interfaz minimalista y moderna, sin tanto ruido visual pero que sea bonita e intuitiva visualmente. Con una gran UI/UX."
  - Acceptance: neutral surfaces; color only for agent identity and status; light and dark themes from design tokens; usable at 1280 px and down to 768 px without horizontal scroll; keyboard navigation and visible focus on every interactive block.
- **S3** Claude at the center: "tú ícono de Claude como pieza central y cerebro del flujo de trabajo, en donde se vea como vas delegando tareas y prompts a knit".
  - Acceptance: a Claude block is the visual origin of the flow and shows what it delegated (plan, tasks, prompts).
- **S4** Wires and queue: "tipo que se vea como una especie de cableado con las instrucciones llegando a knit, a lo mejor si hay varias que se vea como una cola."
  - Acceptance: wires between blocks; a pulse travels when a task is dispatched, a prompt is sent or a result returns; pending tasks appear as an ordered queue at Knit's input; animations are disabled under `prefers-reduced-motion`.
- **S5** Expandable blocks: "Si corresponde, al ser un gran flujo de trabajo, todo en bloques que sean expandibles o den detalle al abrir."
  - Acceptance: Claude, Knit, Cursor, each task and each attempt open to show detail, down to the full agent timeline.
- **S6** Cursor identity: "al final de esto estaría como la cara de Cursor, igual con su icono y demás, como manteniendo la identidad de cada bloque."
  - Acceptance: a Cursor block at the end of the flow with its own icon, color and label; while an attempt runs it shows the current thought or tool call.
- **S7** Original brands: "de verdad me gustaría que sean los originales" · "Me gustariá mantener las referencias y estilos originales de cada modelo."
  - Acceptance: blocks use the official Claude and Cursor logos and brand styles. Logo files live in a git-ignored folder (`web/public/brand/`) that the user fills from the official press kits; the app falls back to monograms when a file is missing. Brand colors and styles live in the identity module.
- **S8** Claude like Cursor: "me gustaría que se mostrará todo igual que con Cursor, el razonamiento y demás".
  - Acceptance: Claude's timeline is shown with the same components as Cursor's: messages, tool calls with arguments and results, tokens. Constraint (L6): headless Claude sends its reasoning blocks empty, so reasoning is shown when present and marked "not shared by the agent" otherwise.
- **S9** Control: "Quiero que esta interfaz no solo sea monitoreo, sino que me de control hasta cierto punto."
  - Acceptance, phase A: start a plan, abort a running run, resume a failed or aborted run, retry a failed task, all from the interface, through the existing Knit commands.
- **S10** One workspace: "centralizar todo mi trabajo en esta interfaz más densa. Como que me sirva para tener dos agendes juntos y pueda añadir mis prompts directamente ahí."
  - Acceptance: the user writes prompts to Claude (phase B, any conversation) and to Cursor (phase C, follow-ups on a task) from the interface; each prompt continues that agent's session (`--resume`) and its answer streams live.
- **S11** Derived (Engram handoff, paraphrased): the user wants to see the agents' full interaction in real time, "not a black box".
  - Acceptance: new agent events appear within about 1 s of being written; a reconnecting browser resumes from the last event id without gaps or duplicates.
- **S12** Derived from S9–S10: the server can launch agents that have no sandbox, so it must not be reachable by other machines or other websites.
  - Acceptance: binds to `127.0.0.1`; every request needs a per-launch token; mutating requests check `Origin` and `Host`; `knit ui [--port <n>] [--data-dir <dir>]` documented in help and docs.
- **S13** One workflow: "Quiero que veas esto de Knit como una forma de facilitar y juntar Claude con Cursor como un solo flujo de trabajo, con el objetivo de optimizar el uso de tokens, centralizar la lógica y tener todo en una sola interfaz donde pueda revisar todo."
  - Acceptance: token usage is visible per agent for every turn, attempt, session and run; Knit's verification stays deterministic and never calls a model; Cursor runs keep self-contained prompts with no memory MCP; conversations, plans, runs, diffs and PRs are all reachable from the interface.
- **S14** Plan like in the terminal: "Donde pueda planificar inicialmente con Claude de la misma manera que estamos haciendo acá, cuando pasemos al desarrollo pasar al orquestador y al final al desarrollo con Cursor."
  - Acceptance: a Claude session runs in the target repository with the user's own Claude configuration (CLAUDE.md, rules, skills, MCP servers such as Engram), so planning behaves as it does in a terminal session; sessions persist and can be resumed later.
- **S15** Handoff only for ready development: "no siempre todo lo que mande a Claude debe ir al orquestador y luego Cursor, solo lo que implique un desarrollo ya con la planificación lista."
  - Acceptance: a Claude turn never starts a run by itself. A run starts only when a plan file exists, passes `knit validate`, and the user launches it from the interface. The run keeps a link to the session whose plan it executes.
- **S16** Chat flexibility: "poder tener la misma flexibilidad e chats e interfaz por el lado de Claude y Cursor, por ejemplo, poder cambiar de chats, modelos, usar comandos, como /usage, /clear, etc. y demás".
  - Acceptance: for each agent, the user can list, switch and resume sessions, start a new one (`/clear`), pick the model per turn, open a command palette built from the agent's own command list, see plan usage (`/usage`) when the agent reports it, and copy the command that continues the same session in a terminal.
- **S17** Files: "a lo mejor a futuro una visual de los archivos en un apartado para saber que está pasando y que se va cambiando."
  - Acceptance: phase A shows each task's diff (from its start commit to its last commit); phases B and C show the files an agent touches while a turn runs; phase E adds a file explorer.

### Decisions and assumptions

- **D1 (accepted, L11)** Frontend stack: Vite + React + TypeScript in `web/`, built to `dist/web` and served by `knit ui`. Reason: container-presentational and atomic design are the user's known patterns; Vite 7 runs on the installed Node 20.20.
- **D2** Live transport: Server-Sent Events over a polled read of SQLite (about 500 ms), event ids as SSE ids. Commands go through plain HTTP `POST`.
- **D3** Runs stay one-shot processes: the server starts `knit run` / `knit resume` as detached children and aborts them by signalling their process group, so a run survives the interface being closed. Needs the run's pid in the database (T1).
- **D4** Claude is driven through `claude -p --output-format stream-json --verbose --resume`, which uses the Pro subscription. The Agent SDK is not used: its docs expect API key auth (L6).
- **A1** Every event records which agent produced it (`claude` or `cursor`), from T1, so phases B and C need no rework of the timeline.

- **D5 (Q2, accepted L9)** Agent configuration in two levels. Level 1: a per-turn profile (model, effort, permission mode) passed as CLI flags, next to the prompt composer. Level 2 (phase D): an editor for the files the CLIs read (Claude: `CLAUDE.md`, `.claude/rules/`, `settings.json`; Cursor: `.cursor/rules/`, `~/.cursor/cli-config.json`, `mcp.json`), project and global, always showing a diff before saving. Because Knit edits the same files, a `claude` or `agent` session opened in a terminal sees the same configuration.
- **D6** Claude sessions run with the user's normal Claude configuration (S14). Cursor runs keep MCP disabled and self-contained prompts (S13).
- **D12 (accepted L15)** Delivery as stacked PRs to `main`, in order. Each slice is about 400 authored changed lines or less, with its tests and docs; each PR targets the previous slice's branch until its parent merges, then is retargeted to `main`. A task whose Risk line names an item (T1, T3, T4, T8, T10, T11, T15, T16) gets its own commit. Slice 0 is the foundations already written (`CLAUDE.md` router, `.claude/rules/`, `docs/web-interface.md`, this document, `.gitignore`); later slices follow the task order and are recorded in the Tasks table as commits land. Push, PR creation and merge stay the user's decisions.
- **D7** The handoff contract is the existing plan format (`docs/plan-format.md`). A `knit-plan` skill teaches Claude to write a valid plan and run `knit validate`; the interface detects the plan, shows it as a draft with its validation result, and the user launches it.
- **D8 (Q3.1, accepted L13)** One agent-agnostic model for sessions, turns and timelines. Each agent adapter declares its capabilities (resume, models, command list, visible reasoning, plan usage) and the interface renders from them, never from the agent's name. A new agent is an adapter plus an identity.
- **D9 (Q3.2)** The command palette is fed by the agent's own list (Claude: `system/init.slash_commands`, minus `terminal_slash_commands`). Session commands are Knit-native: `/clear` starts a new session, switching chats uses the session list, `/model` sets the turn profile, `/usage` opens a panel built from `rate_limit_event` and `result.usage`. Other commands are sent to the agent as the prompt.
- **D10 (Q3.3)** Every session shows the terminal command that continues it (`claude --resume <id>`, `agent --resume <chatId>`), so anything Knit lacks stays one copy away. Knit does not chase parity with either agent's own UI.
- **D11 (Q3.4)** Files are staged: task diff in phase A, live file activity in phases B and C (paths from tool calls plus `git status` of the worktree), file explorer in phase E.
